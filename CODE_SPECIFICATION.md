# Техническое задание по коду Telegram-бота учёта продукции

## 1. Назначение документа

Этот документ переводит функциональные требования из `READme.md` в требования к структуре и коду проекта. Он описывает:

- ответственность модулей;
- существующие классы и методы;
- методы, которые необходимо добавить;
- структуру базы данных;
- основные пользовательские сценарии;
- правила валидации, обработки ошибок и приёмки.

Обозначения статуса:

- **реализовано** — код присутствует и в основном выполняет задачу;
- **частично** — код присутствует, но не покрывает весь сценарий или содержит дефект;
- **не реализовано** — требуется разработка.

## 2. Назначение системы

Telegram-бот предназначен для учёта замороженной и размороженной продукции на предприятии общественного питания. Система должна:

1. хранить справочник товаров и сроки хранения;
2. учитывать поступления продукции в морозильник;
3. создавать отдельные партии при разморозке;
4. автоматически рассчитывать срок годности каждой партии;
5. показывать остатки и истекающие партии;
6. оформлять полную продажу, частичную продажу и списание;
7. хранить историю операций;
8. отправлять ежедневные уведомления;
9. разграничивать права администратора и сотрудника.

## 4. Целевая архитектура

Код должен быть разделён на три слоя:

```text
Telegram handlers
       ↓
StorageService — проверки и бизнес-правила
       ↓
Database — SQL, транзакции и получение данных
```

### Правила разделения ответственности

- `telegram/handler.py` принимает сообщения и callback-запросы, управляет диалогом и форматирует ответы. SQL в этом модуле запрещён.
- `storage/storage_service.py` проверяет входные данные, рассчитывает результат операций и вызывает методы базы данных. Этот слой не должен зависеть от `aiogram`.
- `storage/db.py` выполняет SQL-запросы и транзакции. Этот слой не должен формировать Telegram-сообщения.
- `main.py` только собирает зависимости, регистрирует router, запускает фоновые задачи и polling.
- `google/upload_db.py` отвечает только за резервное копирование базы данных, если эта возможность будет включена.

Все операции, изменяющие сразу несколько таблиц, должны выполняться в одной транзакции. Например, разморозка должна либо одновременно уменьшить остаток в морозильнике и создать партию в холодильнике, либо не изменить ничего.

## 5. Точка входа — `main.py`

### Существующее состояние

#### `async main() -> None` — реализовано частично

Назначение:

1. создать `Bot` из `TELEGRAM_BOT_TOKEN`;
2. создать `Dispatcher`;
3. подключить `telegram.handler.router`;
4. запустить long polling.

Перед запуском polling необходимо дополнительно:

- проверить, что токен задан;
- создать/обновить схему базы данных;
- создать экземпляры `Database` и `StorageService`;
- передать зависимости обработчикам через контекст `Dispatcher` либо middleware;
- зарегистрировать ежедневную задачу уведомлений;
- корректно закрыть сессию бота и фоновые задачи при остановке.

Ожидаемая схема запуска:

```python
async def main() -> None:
    settings = load_settings()
    database = Database(settings.db_path)
    database.init_db()
    service = StorageService(database)
    # Регистрация router, service и планировщика.
    # Запуск polling.
```

## 6. Работа с базой данных — `storage/db.py`

### 6.1. Существующий класс `Database`

#### `_init_db(self, path_to_db="data/database.db") -> None` — частично

Создаёт таблицы `products`, `fridge` и `freezer`.

Проблемы текущей реализации:

- нет таблиц пользователей, истории операций и настроек;
- нет внешних ключей, ограничений положительного количества и уникальности товара в морозильнике.


#### `get_conn(self) -> sqlite3.Connection` — реализовано частично

Открывает соединение с `storage/users.db` и задаёт `sqlite3.Row` как `row_factory`.

Требование: путь к базе должен приходить в `Database.__init__`, а не быть захардкожен. Для каждого соединения следует включать внешние ключи командой `PRAGMA foreign_keys = ON`.

#### `cursor(self)` — реализовано

Контекстный менеджер курсора:

- открывает соединение;
- передаёт курсор вызывающему коду;
- выполняет `commit` при успехе;
- выполняет `rollback` при исключении;
- всегда закрывает соединение.

Возврат из блока без исключения считается успешной операцией и приводит к `commit`. Поэтому ожидаемые бизнес-ошибки нельзя обрабатывать после уже выполненного изменения данных: все проверки должны предшествовать изменениям.

#### `new_fridge_product(self, product_name: str, quantity: int) -> str` — частично

Текущая логика:

1. получает остаток товара в `freezer`;
2. уменьшает его на `quantity`;
3. получает срок хранения из `products`;
4. рассчитывает даты добавления и окончания срока;
5. создаёт отдельную запись в `fridge`.

Обязательные исправления:

- проверять, что `quantity` — положительное целое число;
- корректно обрабатывать отсутствие строки в `freezer`: сейчас `fetchone()[0]` вызывает исключение;
- сначала проверить существование товара и достаточность остатка, затем изменять данные;
- не списывать морозильный остаток, если товар отсутствует в справочнике;
- хранить дату и время, а не только дату;
- возвращать структурированный результат, а не готовый текст Telegram-сообщения;
- переименовать метод в `move_to_fridge(...)` или `create_defrost_batch(...)`.

#### `expire_product(self)` — частично

Возвращает две коллекции: уже просроченные партии и партии, срок которых заканчивается сегодня. Если записей нет, возвращает `False`.

Требования:

- переименовать в `get_expiring_batches(...)`;
- всегда возвращать один тип результата, например `tuple[list[Batch], list[Batch]]`;
- принимать дату/временную зону для тестируемости;
- включать `expiration_date` в возвращаемые данные;
- не смешивать выборку истекающих партий с их изменением или удалением.

#### `clear_expired_product(self, id, quantity: int)` — частично

Уменьшает количество в партии `fridge`; если списывается весь остаток, удаляет партию.

Требования:

- использовать имя `batch_id`, а не встроенное имя `id`;
- проверять положительность количества;
- не разрешать списать больше остатка;
- фиксировать причину и количество в журнале операций;
- различать продажу и списание;
- возвращать явный результат успеха или ошибку вместо `None`;
- сохранять историю до удаления партии.

#### `new_delivery(self, product_name: str, quantity: int) -> str` — частично

Добавляет новую позицию в морозильник или увеличивает существующий остаток.

Требования:

- проверять наличие товара в справочнике;
- проверять положительность количества;
- обеспечить уникальность `freezer.product_name`;
- записывать операцию поступления в историю;
- возвращать данные операции, а не пользовательский текст.

#### `export_fridge(self) -> list[sqlite3.Row]` — реализовано частично

Возвращает все партии холодильника с идентификатором, названием, количеством, датой добавления и сроком годности.

Требования: переименовать в `list_fridge_batches(...)`, добавить сортировку по
`expiration_date`. Просроченные партии определяются по сроку годности, отдельный
статус партии не используется.

#### `export_freezer(self) -> list[sqlite3.Row]` — реализовано частично

Возвращает остатки морозильника.

Требования: переименовать в `list_freezer_stock()` и сортировать результат по названию товара.

Следует определить отдельные исключения, чтобы Telegram-слой мог выдавать понятный ответ:

## 8. Telegram-слой — `telegram/handler.py`

### Существующее состояние

Создан `Router` и обработчик:

```python
@router.message(CommandStart())
async def start_command(message: types.Message): ...
```

Обработчик **не завершён**: `message.answer()` вызывается без текста. Импорт `Command` пока не используется.

### Требуемые обработчики

Для многошаговых операций следует использовать FSM `aiogram`. В состоянии FSM необходимо хранить только временные данные диалога; постоянные данные хранятся в SQLite.

```python
start_command(message)                         # /start и главное меню
show_main_menu(message_or_callback)            # меню с учётом роли

start_defrost(callback)                        # выбор товара
select_defrost_product(callback, state)        # выбранный товар
select_defrost_quantity(message_or_callback, state)
confirm_defrost(callback, state)               # вызов service.defrost

show_due_today(callback)                       # истекает сегодня
show_stock(callback)                           # морозильник + активные партии
start_disposal(callback)                       # просроченные/истекающие партии
sell_all(callback)                             # продано всё
start_partial_sale(callback, state)            # запрос количества/остатка
finish_partial_sale(message, state)            # частичная продажа
write_off_all(callback)                        # не продано
show_write_off_history(callback)               # журнал списаний

show_product_management(callback)              # только admin
add_product(message_or_callback, state)         # только admin
edit_product(message_or_callback, state)        # только admin
delete_product(callback)                       # только admin
show_user_management(callback)                 # только admin
add_user(message_or_callback, state)             # только admin
set_user_role(callback)                        # только admin
set_user_active(callback)                      # только admin
set_notification_time(message, state)          # только admin

cancel_action(message_or_callback, state)       # отмена любого FSM-сценария
handle_storage_error(event, exception)          # понятная прикладная ошибка
```

### Главное меню

Сотруднику доступны кнопки:

- «📦 Достать из заморозки»;
- «⚠ Сегодня заканчивается срок»;
- «🗑 Списание»;
- «📊 Остатки»;
- «📋 История списаний».

Администратору дополнительно доступны:

- «⚙ Управление товарами»;
- «👥 Управление сотрудниками»;
- «🕘 Время уведомлений».

Callback-данные должны содержать действие и устойчивый идентификатор записи, например `batch:sell_all:42`, а не название товара.

## 9. Уведомления

Требуется фоновая корутина:

```python
async def send_expiration_notifications(
    bot: Bot,
    service: StorageService,
) -> None: ...
```

Она запускается ежедневно в настроенное локальное время и:

1. получает партии, срок которых истекает сегодня;
2. формирует одно сводное сообщение;
3. отправляет его всем активным получателям уведомлений;
4. не отправляет повторное уведомление за тот же день;
5. журналирует ошибки отправки, не останавливая polling.

Все расчёты должны использовать явно заданную временную зону приложения. Время по умолчанию — `09:00`, пока администратор не изменил настройку.

## 10. Google-выгрузка — `google/upload_db.py`

Файл пустой. Выгрузка в Google не указана как обязательная функция в `READme.md`, поэтому модуль считается дополнительным.

Если резервное копирование требуется, минимальный интерфейс:

```python
def upload_database(db_path: str, credentials_path: str,
                    folder_id: str) -> str: ...
```

Метод должен загружать согласованную резервную копию SQLite, возвращать идентификатор удалённого файла и не содержать секреты в коде. Перед копированием активной БД следует использовать SQLite Backup API, а не копировать файл во время записи.

## 11. Целевая схема SQLite

### `products`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK | Идентификатор товара |
| `name` | TEXT | UNIQUE, NOT NULL | Название |
| `fridge_storage_days` | INTEGER | NOT NULL, CHECK > 0 | Срок после разморозки в днях |
| `freezer_storage_days` | INTEGER | NULL или CHECK > 0 | Допустимый срок в морозильнике в днях |
| `category` | TEXT | NULL | Категория |
| `is_active` | INTEGER | NOT NULL, default 1 | Архивирование без потери истории |

### `freezer_stock`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `product_id` | INTEGER | PK, FK → products | Один агрегированный остаток товара |
| `quantity` | INTEGER | NOT NULL, CHECK > 0 | Остаток в морозильнике; при нуле строка удаляется |
| `updated_at` | TEXT | NOT NULL | Последнее изменение |

### `fridge_batches`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | Идентификатор партии |
| `product_id` | INTEGER | NOT NULL, FK → products | Товар |
| `initial_quantity` | INTEGER | NOT NULL, CHECK > 0 | Количество при разморозке |
| `quantity` | INTEGER | NOT NULL, CHECK > 0 | Текущий остаток; при нуле строка удаляется |
| `defrosted_at` | TEXT | NOT NULL | Дата и время разморозки ISO 8601 |

## 12. Модели данных

Для передачи данных между слоями рекомендуется использовать `dataclass`:

```python
@dataclass(frozen=True)
class Product:
    id: int
    name: str
    fridge_storage_days: int
    freezer_storage_days: int | None
    category: str | None

@dataclass(frozen=True)
class Batch:
    id: int
    product_id: int
    product_name: str
    initial_quantity: int
    quantity: int
    defrosted_at: datetime
    expires_at: datetime

@dataclass(frozen=True)
class Operation:
    id: int
    operation_type: str
    product_name: str
    batch_id: int | None
    quantity: int
    reason: str | None
    created_at: datetime
    created_by: int
```

Сырые `sqlite3.Row` не должны выходить за пределы слоя `Database`.

## 13. Валидация и бизнес-правила

1. Любое количество — целое число больше нуля.
2. Название товара после удаления пробелов не может быть пустым.
3. Имена товаров уникальны без учёта регистра.
4. Разморозить можно не больше текущего остатка морозильника.
5. Продать или списать можно не больше текущего остатка партии.
6. При нулевом остатке строка товара в морозильнике или партия в холодильнике
   физически удаляется. Соответствующая операция сохраняется в журнале.
7. Срок хранения задаётся целым количеством дней; срок годности считается как
   `defrosted_at + timedelta(days=fridge_storage_days)`.
8. Все даты хранятся в ISO 8601; преобразование в локальное отображение выполняется в Telegram-слое.
9. Денежные и количественные операции не используют `float`.
10. Проверка роли выполняется и в интерфейсе, и в сервисном слое.
11. Партии и операции не объединяются только потому, что относятся к одному товару.
12. Любая неуспешная составная операция полностью откатывается.

## 14. Основные сценарии

### Разморозка

1. Пользователь нажимает «Достать из заморозки».
2. Бот показывает товары с положительным остатком.
3. Пользователь выбирает товар и количество.
4. `StorageService.defrost` валидирует запрос.
5. `Database.create_defrost_batch` в одной транзакции уменьшает морозильный остаток и создаёт партию.
6. Бот показывает товар, количество, время разморозки и срок годности.

### Продано частично

1. Пользователь выбирает партию.
2. Бот запрашивает проданное количество или оставшийся остаток; интерфейс должен явно указывать, какое значение ожидается.
3. Сервис проверяет значение.
4. База уменьшает остаток партии и добавляет операцию `sale`.
5. При нулевом остатке партия удаляется из `fridge_batches`.

### Не продано

1. Пользователь выбирает истёкшую или истекающую партию.
2. Сервис получает полный остаток партии.
3. База создаёт операцию `write_off` с причиной и удаляет партию в одной
   транзакции.
4. Запись появляется в истории списаний.

## 15. Логирование и обработка ошибок

- При запуске логируются версия приложения, путь к БД без секретов и успешная инициализация.
- Бизнес-ошибки логируются на уровне `INFO` или `WARNING` и преобразуются в понятный ответ пользователю.
- Неожиданные исключения логируются с traceback на уровне `ERROR`; пользователю отправляется нейтральное сообщение.
- В логи запрещено писать токен бота, содержимое `credentials.json` и другие секреты.
- Ошибка одного Telegram-обновления или одного уведомления не должна останавливать бота.

## 16. Тестирование

### Модульные тесты `Database` и `StorageService`

Минимальный набор:

- инициализация пустой временной БД;
- добавление, изменение и архивирование товара;
- новое поступление и суммирование морозильного остатка;
- успешная разморозка;
- отказ при недостаточном остатке без частичных изменений;
- расчёт срока годности в днях;
- сохранение двух отдельных партий одного товара;
- выборка просроченных и истекающих сегодня партий;
- полная и частичная продажа;
- полное списание с сохранением причины;
- запрет отрицательного и нулевого количества;
- проверка прав сотрудника и администратора;
- rollback при ошибке внутри составной операции.

### Тесты Telegram-слоя

- `/start` показывает правильное меню для каждой роли;
- callback с несуществующим `batch_id` даёт понятную ошибку;
- некорректное количество не завершает FSM и предлагает повторить ввод;
- отмена очищает FSM;
- административные действия недоступны сотруднику;
- успешные операции вызывают соответствующий метод сервиса ровно один раз.

## 17. Критерии готовности

Функциональность считается готовой, когда:

1. бот запускается на чистой базе без ручного создания таблиц;
2. все пункты главного меню выполняют завершённый сценарий;
3. разморозка атомарно меняет морозильник и создаёт отдельную партию;
4. остатки корректно разделены на активные, истекающие сегодня и просроченные;
5. продажи и списания меняют остаток и сохраняют историю;
6. уведомление приходит один раз в день в настроенное время;
7. права ролей проверяются на уровне бизнес-логики;
8. ошибки ввода не приводят к падению polling;
9. автоматические тесты покрывают критические операции и проходят без ошибок;
10. секреты отсутствуют в исходном коде и истории новых коммитов;
11. README содержит команды установки зависимостей, настройки окружения и запуска.

## 19. Отложенная функциональность

На текущем этапе не входят в объём реализации:

- самостоятельная или автоматическая регистрация пользователей; сотрудников
  вручную добавляет администратор, а `/start` только проверяет наличие активной
  учётной записи;
- статистика за день, неделю и месяц, включая метод `get_statistics`, сервисный
  сценарий, Telegram-обработчик, пункт меню и отдельные тесты статистики.

Журнал `operations` и история списаний сохраняются в текущем объёме работ, чтобы
статистику можно было добавить позже без потери исходных данных.
